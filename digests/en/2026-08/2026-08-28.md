## Commits

Today's seven commits primarily focused on stability and correctness, addressing several critical bugs in the query planner, shared memory management, and parallel vacuum operations.

### ⭐ [Fix incorrect multi-column RANGE partition pruning](https://github.com/postgres/postgres/commit/6e5d5680b555523a3d5c547aa22df0267860344a)
**David Rowley**

This commit fixes a bug in partition pruning for RANGE partitioned tables with multi-column partition keys, where providing quals for only a prefix of the key could lead to incorrect pruning decisions. The issue stemmed from an incorrectly coded loop bound, causing both over-pruning and under-pruning of partitions.

---

### ⭐ [Perform join removal by editing the query's jointree.](https://github.com/postgres/postgres/commit/2ebf25e7d70a8fce31ace78d723fa9271ab8af72)
**Tom Lane**

This commit refactors the join removal process in the planner to directly edit the query's jointree, rather than trying to partially update derived planner data structures. This change addresses a long-standing issue (Bug #19560) where inconsistent updates could lead to incorrect query plans after join removal.

---

### [Propagate rebalanced cost limit to parallel vacuum workers](https://github.com/postgres/postgres/commit/6c5f1d6074208146930b67c2054509c3e82f6f7f)
**Daniel Gustafsson**

This fix ensures that parallel autovacuum workers correctly receive updated cost limits after `AutoVacuumUpdateCostLimit()` runs, preventing them from operating at stale, potentially double or half, the configured budget until the next SIGHUP. It calls `parallel_vacuum_propagate_shared_delay_p` to push the new limit to shared memory.

---

### [Track which shmem areas have been fully initialized](https://github.com/postgres/postgres/commit/07fdee7c8a8b415fb3a2991e7aea34f08975d445)
**Heikki Linnakangas**

This commit adds an explicit 'initialized' flag to each shared memory area, improving robustness when `SHMEM_CALLBACKS_ALLOW_AFTER_STARTUP` is used. This ensures that shared memory areas are clearly marked if their initialization fails midway, preventing them from being left in an indeterminate state.

---

### [Fix backend state after a failed after-startup shmem request](https://github.com/postgres/postgres/commit/c54b6979e033c6182518d4b33feb35771ae738ae)
**Heikki Linnakangas**

Building on the shared memory improvements, this commit fixes the backend's state if an error occurs during an after-startup shared memory request. Previously, `shmem_request_state` could be left in an incorrect state, and `pending_shmem_requests` not properly cleaned up, leading to subsequent issues or assertion failures.

---

### [Make platform guards in two regression tests match meson builds](https://github.com/postgres/postgres/commit/4d5fdb21ddda46972d7703562c5ad4076feae8b8)
**Andrew Dunstan**

This commit updates platform guards in the `collate.linux.utf8` and `infinite_recurse` regression tests to correctly match the host triplet format used by meson builds. This resolves a regression in v16 where these tests were not running as intended on meson builds for specific platforms.

---

### [Propagate disabled_nodes to single-child Append paths](https://github.com/postgres/postgres/commit/de5659440dbcfe0ef61b474cec0e5ec50a9c3841)
**Richard Guo**

This commit addresses a regression in v18 where `create_append_path()` failed to propagate `disabled_nodes` when an Append had a single child. This oversight could lead to the planner incorrectly selecting a disabled path over an enabled one, impacting query performance.
