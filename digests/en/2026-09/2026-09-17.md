### ⭐ [Change GEQO fitness comparisons to consider disabled_nodes.](https://github.com/postgres/postgres/commit/c9c660e6ae03027615adff90cf4b26da5f8f97c1)

This commit corrects an oversight in the GEQO (Genetic Query Optimizer) fitness comparison logic, which previously only considered the total cost of a plan. It now properly incorporates the number of `disabled_nodes` introduced in v18, preventing GEQO from potentially preferring less optimal plans.

### ⭐ [pg_plan_advice: Disallow partition name without partition schema.](https://github.com/postgres/postgres/commit/63920eb099ab7e0e9d9eb49a3aa392c9441d52ef)
**Robert Haas**

This commit addresses a design flaw in `pg_plan_advice` where specifying a partition name without its schema could lead to incorrect advice feedback, even if enforcement worked. It now requires partitions to be qualified with their schema, ensuring consistency between advice generation and feedback.

### [pg_plan_advice: Fix defects in JOIN_ORDER advice feedback.](https://github.com/postgres/postgres/commit/e1d8f81d4961ca6c4228eb9a3ab5d36168008e42)
**Robert Haas**

This commit rectifies several issues in the `pg_plan_advice` feedback mechanism, specifically concerning `JOIN_ORDER` advice. Previously, the system failed to correctly match unordered sublists within `JOIN_ORDER` specifications, leading to inaccurate feedback when advice was supplied externally.

### [Have the REPACK decoding worker use timeout values from the steering backend](https://github.com/postgres/postgres/commit/a62ff0829d6b151a7107f6ae7f7f90b52405a247)
**Álvaro Herrera**

This change ensures that `REPACK` decoding workers inherit `lock_timeout` and `transaction_timeout` values from the steering backend, rather than defaulting to role- or database-level settings. This prevents unintended timeout cancellations during `REPACK` operations by allowing session-local `SET` commands to propagate to the worker.

### [Tolerate partial pgstats entries in pgstat_gc_entry_refs()](https://github.com/postgres/postgres/commit/16706f1f4dc202d502f07f7b14bb600eb0daef92)

This commit improves the robustness of `pgstat_gc_entry_refs()` by making it tolerant of partially filled `pgstats` entries. Previously, an `ERROR` during `pgstat_get_entry_ref()` could leave an entry in an inconsistent state, leading to a crash in the garbage collection routine.

### [doc: Say which LSN gives read-your-writes with WAIT](https://github.com/postgres/postgres/commit/2af020eacb8b74232a0570f72a05dd1f274f68de)
**Alexander Korotkov**

The documentation for `WAIT` in `standby_replay` mode has been clarified to specify that the LSN target must be at or after the end of the commit record for true read-your-writes consistency. This corrects previous ambiguities that could lead users to wait on an LSN insufficient to guarantee the transaction is fully applied.

### [doc: Explain when to use the WAIT NO_THROW option](https://github.com/postgres/postgres/commit/e87c55f4db3fc3723e1f5d8ade7278e33bbb869)
**Alexander Korotkov**

This documentation update provides more context on when to use the `WAIT NO_THROW` option, explaining its suitability for applications that handle timeout or recovery status as part of normal control flow. It emphasizes the need to check the returned status and clarifies that `NO_THROW` only affects how those two wait outcomes are reported.

### [Fix assertion after aborting internal subtransaction at transaction end](https://github.com/postgres/postgres/commit/999ce9bcd80890c3d723e113bb0337c900f9f249)
**Fujii Masao**

This commit resolves an assertion failure that could occur when an internal subtransaction was aborted during `COMMIT` or `PREPARE TRANSACTION`. Such scenarios, like a deferred constraint trigger raising an error caught by an exception block, previously led to a transaction state assertion failure.

### [Distinguish publication exclusions in object addresses.](https://github.com/postgres/postgres/commit/94670ba6d560b0738992b9bb7d0313d7d90af1d1)
**Amit Kapila**

This commit improves logical replication's object address reporting by correctly distinguishing between explicitly published relations and tables excluded from `FOR ALL TABLES` publications. `EXCEPT` entries are now reported as "publication excluded relation" in dependency messages and `pg_identify_object()` functions, providing more accurate information.
